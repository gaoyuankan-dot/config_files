In plain words

When a program starts, it reads a few small text files from your home folder: zsh reads ~/.zshrc, Vim reads ~/.vimrc, git reads ~/.config/git/config. This repo keeps all of them in one folder, home/. install.sh puts a symlink in your home folder for each one, so every program reads the repo's copy and git sees every change.

Picture it as a theatre

home/ is the script library. Each program is an actor who walks on at a fixed cue (a terminal opens, a prompt is drawn, Vim starts) and reads only its own pages. The symlinks are notes on the stage door: “your pages are in the library”. Change a page and the next performance changes, on every stage that pulls the library.

Part 7

Findings from drawing the plates

Three loose ends and two notes. The loose ends were fixed on 2026-10-21, each with a regression test that failed before the fix; the full write-up is docs/FIX-NOTES.md.

  • fixed

    install.sh would link Vim's swap file

    It links every file under home/, editor litter included. With Vim editing ~/.vimrc, the swap file sits at home/.vimrc.swp.

    Evidence: ./install.sh --dry-run printed link ~/.vimrc.swp and “Done: 1 linked, 17 already in place”.

    Fixed: its find skips *.sw? and *~. test.sh section 3 plants both in a fake repo and checks that neither gets linked; with a real swap file present the dry run now says “0 linked, 17 already in place”.

  • fixed

    git/ignore says “the vimrc keeps them in ~/.vim”

    home/.vimrc sets only 'undodir'; swap files land next to the file being edited.

    Evidence: five swap files in the repo today (.install.sh.swp, home/.vimrc.swp, three in scripts/), with three Vim sessions open on it. They are yours, so they were left alone.

    Fixed: the comment now says Vim writes them next to the file it edits (for a symlink, next to its target), not into ~/.vim. GUIDE §1.4 and LEARN-AND-SYNC repeated the old claim; corrected too.

  • fixed

    .editorconfig does nothing in this Vim

    Vim 9.1 ships EditorConfig support as an optional package. home/.vimrc never runs packadd! editorconfig.

    Evidence: /usr/share/vim/vim91/pack/dist/opt/editorconfig exists; the startup trace loaded 0 editorconfig scripts. VS Code needs its extension too.

    Fixed: silent! packadd! editorconfig at line 7, after four indent rules were corrected to match the files (.clang-format, .clang-tidy, *.html, the root vimrc). It works by the path you open, so a dotfile opened through its ~ link still gets your vimrc's indent.

  • note

    Startup time is above the README's number

    Login zsh measured 81 ms (non-login 62 ms) today, median of 8 in a real terminal. The Windows PATH is still appended (10 /mnt/c folders), so the GUIDE's WSL PATH tip (README: 31 ms) is not applied on this machine. Different stopwatches give different numbers; compare runs of the same method.

  • note

    Local main is one commit behind GitHub

    The prompt shows ⇣1: GitHub still has the laptop's commit, and the fresh start in GUIDE §9.5 has not run yet. Until it does, docs/archive/ holds only its README and the root vimrc stays where it is.

Part 8

What to keep, and how to practise

The rules that explain all 21 plates, the trade-offs, and the method used to make them.

Nearest file wins

The tool searches upward from the file you edit and stops at the first match.

clang-formatclangd flags.editorconfig

Later layer wins

Every layer is read; a key set later overrides the same key set earlier.

git configclangd .clangd on config.yamlshell variables

First file only

The program reads the first file that exists and never looks at the rest.

gdblogin bash: .bash_profile

How to improve

  • Now: run GUIDE §9.5 (the three loose ends are fixed).
  • Next: apply the WSL PATH tip and re-measure; decide whether dotfiles opened through ~ should follow .editorconfig too (FIX-NOTES lists the options).
  • Bleeding edge: declarative, templated dotfiles (chezmoi, or Nix Home Manager); deferred zsh plugin loading (zsh-defer) so the prompt appears before plugins finish.

Mental checklist

  1. Which kind of shell is this: login, interactive, and is fd 0 a terminal?
  2. Who sources whom in that mode? (Plate 5)
  3. Is the file I am editing the live one? readlink ~/.zshrc
  4. Is it read once (tmux, gdb, shell rc) or every time (starship, git)?
  5. Which rule decides the winner: nearest, later, or first?
  6. Did I ask the program, or trust a comment? (sourcetrace, :scriptnames, --show-origin, --dry-run)

How these plates were made

1 · Trace the shells

ThinkingComments describe intent. zsh -o sourcetrace and bash's PS4 with -x, run under script so a real terminal exists, report every file actually sourced, including 13 system scripts the repo never mentions.

LessonAsk the program for its load order; do not rebuild it from comments.

2 · Trace Vim, after a false start

ThinkingThe first probe (Vim under script, ended by a timer) never quit. Instead of debugging the probe, the tmux harness that test.sh already proves on every run was reused, and it worked the first time.

LessonWhen a probe hangs, reuse a harness that is already tested.

3 · Cross-check with the source

ThinkingThe trace put gruvbox (#117) just before the LSP modules (#118). The plugin source explains why: both are VimEnter autocommands, they run in definition order, and the vimrc's was defined first.

LessonA trace says what happened; the source says why. Use both.

4 · Let dry runs and counts find bugs

ThinkingDrawing Plate 18 meant running install.sh --dry-run, which printed link ~/.vimrc.swp. Counting scripts for Plate 8 showed 0 editorconfig scripts. Both are fixed now (Findings).

LessonDrawing a mechanism forces you to check it, and checking finds bugs.

The short version. Every startup was traced on this machine instead of read from comments: zsh and bash with source traces, Vim with :scriptnames inside a tmux terminal after a first probe hung, and tmux, git and gdb by asking each program. The traces matched the configs. The cross-checks turned up three loose ends, since fixed: install.sh would link a Vim swap file, a git/ignore comment was stale, and .editorconfig was inert in Vim.

The transferable principles (the part to keep):

  1. Ask the program, not the comment: every tool here can report what it loaded.
  2. Learn the precedence rule (nearest, later, first) before you edit a config.
  3. Two independent sources, a trace and the source code, beat one.
  4. Reuse proven harnesses, such as tmux as a fake terminal, instead of inventing probes.
  5. A dry run is a free test. Run it whenever you draw or change a flow.
